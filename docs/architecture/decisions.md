# Architecture Decision Records

Decisions taken during implementation where the specification left a choice
open. The governing rule is: prefer the simplest robust production-grade
solution, preserve extensibility, and write the decision down.

---

## ADR-0001 — One Python distribution assembled from many package roots

**Context.** The Build Specification mandates a physical layout of
`apps/`, `packages/`, `agents/`, `integrations/`, `database/`. Fifteen separate
Python distributions would mean fifteen `pyproject.toml` files, fifteen version
numbers and a dependency graph to maintain — distributed complexity in a
modular monolith that explicitly does not want it.

**Decision.** A single distribution (`seo-engine`) whose source is assembled
from many roots. Every root contributes to the implicit namespace package
`seo_engine`, so `packages/memory/seo_engine/memory/` imports as
`seo_engine.memory`. Wheel builds list the roots under
`[tool.hatch.build.targets.wheel] packages`; editable installs list them under
`dev-mode-dirs` (needed because hatchling's editable mode emits one path per
mapped name and would otherwise drop all but the first root).

**Consequences.** The mandated directory tree is preserved exactly; imports are
clean and boundary-revealing; extracting a package into its own distribution
later is a mechanical change because the import path already names the boundary.

## ADR-0002 — Two packages beyond the specified list: `domain` and `engines`

**Context.** The specification's package list has no obvious home for the
persistence layer (ORM models, tenant-scoped repositories, domain services) or
for the deterministic analysis engines (crawler, technical SEO, keyword,
competitor, content, opportunity). Folding persistence into `shared` would make
`shared` the largest package in the repo and blur the boundary the Architecture
Pack cares most about; folding the engines into `knowledge` would misuse a
package reserved for the knowledge graph.

**Decision.** Add `packages/domain/` (ORM models, repositories, domain services)
and `packages/engines/` (deterministic analysis). Every package named in the
specification is still present and keeps its specified responsibility.

**Consequences.** Rule 4 ("no direct database access from agents") becomes
structurally checkable: agents depend on `seo_engine.domain.services`, and
nothing outside `domain` imports `seo_engine.domain.models`.

## ADR-0003 — The repository root *is* `seo-engine/`

**Context.** The specification says "create `seo-engine/`". The provided
repository is already named `SEO-Engine`.

**Decision.** Build at the repository root rather than nesting a redundant
`seo-engine/seo-engine/`. The supplied `.docx` specifications were moved to
`docs/source-material/`.

## ADR-0004 — Migration history is authored one domain at a time

**Context.** A single autogenerated "initial" revision creating 75 tables is
unreviewable, and the specification explicitly names `0001_identity.sql`,
`0002_brands.sql`, `0003_websites.sql`, `0004_search.sql`, `0005_content.sql`.

**Decision.** Eleven revisions, one per domain, matching the specification's
naming. `database/build_migrations.py` regenerates the chain from the ORM models
by scoping autogenerate to one domain's tables at a time (via the
`ALEMBIC_TABLE_SCOPE` environment variable read in `env.py`) and upgrading
between steps. Alembic (Python) is used rather than raw `.sql` files so the
schema has a single source of truth in the ORM and so `downgrade` exists.

**Consequences.** The history reads like the specification. `0001` also creates
the `vector` and `pgcrypto` extensions, so a fresh database needs no manual
preparation.

## ADR-0005 — Tenant isolation is enforced in three layers, not by convention

**Context.** Rule 10 forbids any cross-tenant read. "Remember to filter by
tenant_id" is not an enforcement mechanism.

**Decision.**

1. **Schema.** `TenantOwnedMixin` makes `tenant_id` non-nullable and indexed on
   every tenant-owned table. An integration test asserts no tenant-owned table
   has a nullable `tenant_id`.
2. **Repository.** All reads and writes will go through a tenant-scoped
   repository that injects `WHERE tenant_id = :tenant` (pending — Phase 4).
3. **Session guard.** A `before_flush` hook on the session rejects writing any
   object whose `tenant_id` differs from the tenant the session is bound to,
   raising `TenantIsolationError`. This is the backstop for a repository bug.

`TenantIsolationError` returns HTTP 404, not 403 — confirming that another
tenant's resource exists is itself a leak.

**Note.** `tenant_users` declares `tenant_id` explicitly with a real foreign key
to `tenants` rather than inheriting the mixin, because the membership
relationship needs a resolvable join condition.

## ADR-0006 — External content is a type, not a string

**Context.** Rule 9 and Build Specification §54 require that crawled content
never be treated as instructions, and that the distinction survive into the
agent context layer.

**Decision.** External text is carried by `UntrustedContent`
(`packages/shared/.../untrusted.py`), never by a bare `str`. Three layers:

1. **Typing.** `ContextBlock` raises if a block on the `EXTERNAL_CONTENT`
   channel is marked trusted, so the type system rejects the mistake.
2. **Structural fencing.** `render()` emits a fence tagged with a fresh random
   nonce plus an explicit in-band warning. Page copy cannot predict the closing
   marker, so fence-escape attacks fail.
3. **Detection.** Six injection pattern families are detected and *reported*
   rather than silently stripped — the detection is itself evidence a reviewer
   and the audit log want. Detected content is still rendered inertly, with the
   warning escalated.

**Consequences.** The database mirrors this: `crawl_pages` and `pages` carry
`is_untrusted_external_content` and `injection_findings`.

## ADR-0007 — Absent data stays absent

**Context.** Rules 1 and 14 forbid fabricating volumes, difficulty, rankings,
competitor metrics or AI-search visibility.

**Decision.** Every metric carries a `DataProvenance` label
(`observed` / `estimated` / `inferred` / `user_provided` / `synthetic_demo` /
`unknown`). When no provider is connected, the value is `NULL` and provenance is
`unknown` — there is no default that reads as real. `KeywordMetric` defaults to
exactly this. The AI Search module keeps a separate three-way classification
(`observed` / `inferred` / `unknown`) so proprietary ranking internals are never
presented as facts.

## ADR-0008 — Planned: the LLM is optional, and outputs say which path produced them

**Context.** The vertical slice must run in development without an LLM API key,
but a deterministic stand-in must never be mistaken for model output or for real
external data.

**Decision (recorded now, implemented with the agent runtime).** A model gateway
with `anthropic`, `openai` and `deterministic` providers. The deterministic
provider composes structured output from the run's own observed inputs only — it
invents no external facts. Every `AgentResult` carries `synthesis_mode`
(`llm` / `deterministic` / `hybrid`), persisted on `agent_runs`, so the UI can
label how a narrative was produced. Manifests declare
`model_policy.deterministic_fallback` per agent; agents whose output is
genuinely generative (the content writer) will not silently degrade.
